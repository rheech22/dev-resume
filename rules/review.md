# 독립 리뷰와 종합

리뷰는 이력서를 고치지 않습니다. 여러 관점의 지적을 모아 검증하고, 사용자가 판단할 수 있게 정리해서 보고합니다.

## 1. 준비

처음 실행이 끝나지 않았어도 리뷰를 요청받으면 진행합니다. 이때 아직 확인하지 못한 사실이 무엇인지 리뷰어에게 알리고, 보고에도 적습니다.

`facts`나 workspace의 형식 표시가 낮으면 리뷰 전에 `rules/intake.md`의 "형식 옮기기"를 제안합니다. 사용자가 미루면 옛 형식에서 정정에 해당하는 내용(틀렸다고 확인된 사실)을 찾아 같은 방식으로 다룹니다.

이력서 텍스트는 workspace의 `format`에 맞는 adapter의 읽기 절을 따라 뽑습니다.


- 이력서의 최신 상태를 텍스트로 뽑습니다. 렌더 결과(PDF나 이미지)가 있으면 함께 준비합니다.
- 공고가 있으면 공고 원문을 파일로 저장합니다.
- `facts`의 `제약` 절을 읽어 리뷰어에게 건넬 맥락을 정리합니다. 경력 연수, 하지 않은 일, 공개하지 않을 지표, 의도된 용어입니다.
- `facts`의 `정정` 절과 `확인 중` 사실을 읽어 리뷰어에게 건넵니다. 리뷰어는 이력서 문장이 사실인지 모르므로, 이미 틀린 것으로 확인된 문장을 강점으로 인용할 수 있습니다. `이력서 기재` 상태의 사실은 아직 확인 전일 뿐 틀린 것이 아니므로 리뷰어가 인용해도 됩니다.
- 정정을 이력서에 아직 반영하지 않았으면, 정정을 반영한 리뷰용 사본을 만들어 건넵니다. 사본에서는 해당 문장을 `facts`의 `정정` 절에 적힌 "확인된 사실" 문구로만 바꿉니다. 새로 다듬거나 괄호와 숫자의 위치를 바꾸지 않습니다. 바꾼 문장에는 `[정정]` 표시를 붙이고, 보고에 사본을 썼다고 밝힙니다. 문장을 새로 쓰는 일은 `write` 모드에서 사용자 확인을 받고 합니다.
- `facts`의 `지향` 절을 읽어 리뷰어에게 건넵니다. 리뷰어는 "이 이력서가 지향하는 방향으로 읽히는가"를 함께 판정합니다.

## 2. 리뷰어 고르기

기본 구성은 아래 표에서 "항상"인 3명입니다. 나머지 리뷰어는 조건이 맞을 때 사용자에게 "추가할까요?"라고 제안하고, 사용자가 원할 때만 넣습니다. 사용자가 리뷰어 구성을 미리 말하지 않았으면 기본 3명을 먼저 돌리고, 보고 끝에 추가 리뷰어를 제안합니다. 사용자가 원하면 추가 리뷰어만 돌려 보고를 보탭니다. 사용자가 리뷰어를 더하거나, 빼거나, 처음부터 새로 구성하길 원하면 그 구성을 그대로 따릅니다. 사용자가 정한 리뷰어에게도 3절의 지시 양식과 4절의 종합 규칙은 똑같이 적용합니다.

| 리뷰어 | 보는 것 | 언제 |
| --- | --- | --- |
| 채용 결정권자 | 면접을 볼지, 가장 강한 근거와 해가 되는 부분, 예상 질문. 공고가 있으면 공고 기준, 없으면 지향 직무의 채용 매니저 기준 | 항상 |
| 회의적인 시니어 엔지니어 | 부풀린 주장, 리드와 본문의 불일치, 섹션 간 중복, 외부인이 모를 용어, 기술적 부정확성 | 항상 |
| 채용 담당자와 교열자 | 10초 스캔에서 남는 것, 결과·수치·방법 공식 준수 여부, 분량, 오탈자와 표기 혼용 | 항상 |
| 시각 디자인 리뷰어 | 위계, 간격, 페이지 경계, 스캔 동선 | 렌더 결과(받은 PDF 포함)가 있을 때 제안 |
| 출처 기반 페르소나 | 사용자가 건넨 글이나 영상의 원칙만으로 본 판정 | 사용자가 자료를 건넸을 때 제안 |

### 출처 기반 페르소나

사용자가 이력서 조언 글이나 영상을 건네면, 그 자료의 저자를 페르소나로 삼아 리뷰합니다.

1. 리뷰어가 먼저 자료를 직접 읽습니다. 영상은 자막을 구하고, 구하지 못하면 확인한 부분과 추정한 부분을 나눠 표시합니다.
2. 자료에서 원칙 3~5개를 뽑고, 각 원칙에 출처를 붙입니다.
3. 그 원칙만으로 리뷰합니다. 다른 출처의 조언을 섞지 않습니다.

## 3. 리뷰어에게 건네는 지시

리뷰어는 서로의 결과를 보지 않고 동시에 실행합니다. 각 리뷰어에게 다음을 건넵니다.

- 역할과 관점 (위 표)
- 이력서 텍스트와 렌더 결과의 경로, 공고 경로
- 사용자 제약. "이 제약에 반하는 제안은 하지 않는다"를 명시합니다.
- 정정 목록과 확인 중인 사실. "이 문장을 근거로 칭찬하거나 제안하지 않는다"를 명시합니다.
- 읽기 전용이라는 점. 파일을 고치거나 이력서 도구를 호출하지 않습니다.
- 교열자에게는 `rules/prose.md`의 표기 기준을 건네고, 리뷰 전에 `scripts/check-copy.mjs`를 원고에 돌린 결과를 함께 줍니다.
- 출력 형식과 분량 상한

출력 형식은 다음을 기본으로 합니다.

```text
1. 한 줄 판정: 면접을 볼지, 지향 방향으로 읽히는지, 공고가 있으면 공고에 맞는지를 각각 판정
2. 가장 강한 근거 3개: 이력서 문장 인용
3. 고칠 점 최대 5~8개: 인용 → 문제 → 고칠 방향
   - 사실이 필요한 수정이면 지어내지 말고 "무엇을 물어야 하는지"를 적는다
4. 예상 면접 질문 3개 (결정권자, 시니어만)
```

## 4. 종합

리뷰 결과를 그대로 전달하지 않습니다.

1. **공통 지적을 먼저 둡니다.** 두 명 이상이 같은 문장을 지적했으면 우선순위가 높습니다.
2. **리뷰어가 인용한 문장을 모두 검증합니다.** 지적한 문장뿐 아니라 강점으로 칭찬한 문장도 `facts`와 대조합니다. 확인 중이거나 정정된 문장을 근거로 한 칭찬과 제안은 "사실과 다른 근거"로 분류합니다. "날짜가 밀려 있다" 같은 렌더 관련 주장은 렌더 결과에서 직접 확인하고, 틀린 지적은 "리뷰어 오판"으로 표시합니다.
3. **사용자 제약으로 거릅니다.** 공개하지 않기로 한 지표를 넣으라는 제안, 하지 않은 일을 쓰라는 제안, 의도된 용어를 바꾸라는 제안은 "무시해도 되는 지적"으로 분류합니다.
4. **사실이 필요한 지적은 질문으로 바꿉니다.** 예: "80%가 어디서 나왔는지 의심받는다" → "80%가 캐시 효과인지, 기준값이 몇 초였는지".
5. **기계적 수정과 판단이 필요한 수정을 나눕니다.** 오탈자, 표기 통일, 공백은 바로 고칠 수 있는 목록으로 둡니다.

보고 양식은 `templates/review-report.md`를 따릅니다. 보고와 리뷰어에게 건넨 맥락은 `<home>/reviews/YYYY-MM-DD-review.md`에 저장하고, 실행한 skill 버전을 맨 위에 적습니다. 같은 날 다시 리뷰하면 `-2`, `-3`을 붙여 새 파일로 저장합니다. 이전 보고는 덮어쓰지 않습니다.

리뷰에서 새로 나온 질문은 `facts`의 `확인 필요`에 추가합니다. 리뷰어가 사실과 다르게 말한 내용은 `facts`에 옮기지 않습니다.

## 5. 반영

사용자가 반영을 요청하면 `rules/scope.md`의 순서대로 `write` 모드로 넘어갑니다.

- 근거가 확인된 지적만 고칩니다.
- 사용자만 아는 사실이 필요한 지적은 질문 목록으로 남깁니다.
- 원인 진술을 새로 쓰거나 바꾸면 사용자에게 확인을 받습니다.
