# 근거 수집과 사실 확인

이력서의 모든 문장은 `facts` 파일의 사실에서 나옵니다. 이 문서는 그 사실을 모으고 확인하는 절차입니다.

## 사실의 상태

`facts`의 사실마다 상태를 붙입니다.

| 상태 | 뜻 | 이력서에 쓸 수 있나 |
| --- | --- | --- |
| `이력서 기재` | 기존 이력서에서 가져왔고 아직 확인 전 | 기존 문장 그대로는 유지할 수 있지만, 숫자를 바꾸거나 더 강하게 쓰지 않습니다 |
| `근거 확인` | 저장소, 문서, 공개물로 확인함 | 씁니다 |
| `사용자 확인` | 사용자가 직접 확인해 줌 | 씁니다 |
| `확인 중` | 근거와 기존 이력서가 달라 사용자에게 물어본 상태 | 기존 문장을 더 강하게 쓰지 않고, 리뷰어에게 확인 중이라고 알립니다 |
| `후보` | 근거 자료에서 찾았지만 사용자가 넣을지 정하지 않음 | 쓰지 않습니다 |

근거와 기존 이력서가 다르면 상태를 `확인 중`으로 바꾸고 질문 목록에 넣습니다. 사용자가 답하면 고친 사실과 함께 `사용자 확인`으로 바꿉니다. 기존 이력서의 틀린 문장은 `정정` 절에 `기존 문장 → 확인된 사실`로 남깁니다. 리뷰와 작성이 이 절을 읽습니다.

한 사실의 일부만 확인되면(숫자는 맞고 원인 진술은 다름 등) 상태는 확인된 범위로 정하고, 확인되지 않은 부분은 `메모` 열에 적습니다.

## 1. 출처의 우선순위

1. **사용자의 말**: 본인 몫, 동기, 맥락, 결과, 공개 여부는 사용자만 압니다.
2. **저장소**: 커밋, 코드, 테스트, 설정. 무엇을 언제 누가 했는지 확인합니다.
3. **저장소 문서**: ADR, 설계 문서, 트러블슈팅 기록, 히스토리 문서. 왜 그렇게 했는지 확인합니다.
4. **외부 공개물**: 스토어 페이지, 서비스 URL, 공개 저장소. 링크와 출시 여부를 확인합니다.
5. **이전 이력서**: 문장을 되살릴 후보입니다. 숫자는 다시 확인하기 전에는 그대로 옮기지 않습니다.

## 자료 받기

근거는 저장소에만 있지 않습니다. 메신저 대화, 회의록, 문서 도구의 페이지, 이메일, 파일, 대시보드 화면, 성과 평가, 릴리스 노트, 스토어 페이지, 블로그 글이 모두 근거가 될 수 있습니다.
자료의 종류마다 따로 대응하지 않고, 어떤 자료든 같은 다섯 단계로 흡수합니다.

### 1. 어떤 자료가 있는지 묻기

처음 실행이나 `write` 중에 근거가 부족하면 사용자에게 묻습니다. 자료 이름보다 "무엇을 증명할 수 있는지"로 묻는 편이 잘 떠오릅니다.

```text
이 작업을 뒷받침할 자료가 있나요?
- 언제, 누가 했는지 보여 주는 것: 커밋, 티켓, 릴리스 노트, 메신저 공지
- 왜 그렇게 했는지 보여 주는 것: 설계 문서, 회의록, 논의 스레드
- 결과를 보여 주는 것: 대시보드 화면, 리포트, 성과 평가, 고객 반응
```

### 2. 읽는 방법 정하기

| 상황 | 방법 |
| --- | --- |
| 코드 호스팅의 PR, 이슈, 릴리스 기록 | 연결된 CLI나 도구가 있으면 같은 방식으로 계정을 확인하고 읽습니다. 로컬 git에는 PR 생성·머지·거절 기록이 없습니다 |
| agent에 연결된 도구가 있음 (MCP 등) | 연결된 워크스페이스와 계정이 사용자 본인 것인지 먼저 확인하고 사용자에게 보여 줍니다. 아니면 쓰지 않습니다 |
| 연결된 도구가 없음 | 사용자에게 붙여 넣기, 내보내기 파일, 화면 캡처를 달라고 합니다 |
| 퇴사 등으로 접근할 수 없음 | 사용자의 기억을 받되 상태를 `사용자 확인`으로 두고, 숫자는 범위나 근사치임을 표시합니다 |

회사 계정으로 연결된 도구에서 이직 준비 자료를 만들거나 저장하지 않습니다. 읽기만 하고, 결과는 `home`에 둡니다.

### 3. 사실만 뽑기

자료를 통째로 `home`에 복사하지 않습니다. 채용 공고는 예외입니다. 공개 문서이고 맞춤본과 리뷰가 원문을 다시 읽어야 하므로 원문을 `<home>/jobs/`에 저장합니다. 이력서에 필요한 사실만 뽑아 `facts`에 적고, 출처에는 자료의 종류와 날짜만 남깁니다. 예: `메신저 공지 (2026-07-14)`, `분기 리포트 화면 캡처`.

### 4. 근거의 강도 매기기

| 강도 | 예 | 쓰는 방법 |
| --- | --- | --- |
| 강 | 커밋, 배포 기록, 대시보드 수치, 공식 리포트 | 숫자와 함께 씁니다 |
| 중 | 회의록, 설계 문서, 동료의 메시지 | 사실은 쓰되 숫자는 다른 근거로 한 번 더 확인합니다 |
| 약 | 사용자의 기억, 비공식 대화 | 사용자 확인을 받고, 숫자는 근사치로만 씁니다 |

### 5. 민감 정보 거르기

- 회사 내부 수치, 고객 이름, 매출, 동료의 이름과 발언은 이력서에 쓰지 않습니다. 공개해도 되는지 모르면 `제약`에 질문으로 남깁니다.
- 내부 수치는 비율이나 변화량처럼 공개 가능한 형태로 바꿀 수 있는지 사용자에게 묻습니다.
- 메신저, 이메일의 원문은 인용하지 않습니다.

## 2. 본인 몫 확인

workspace의 `sources`에 적힌 author 이름으로 커밋을 나눠 봅니다.

```bash
git shortlog -sn --no-merges
git log --author="<이름>" --format='%ad %s' --date=short -- <경로>
git log --format='%an' -- <문서 경로> | sort | uniq -c
```

- 같은 사람의 author 이름이 여러 개일 수 있습니다. 사용자에게 확인한 이름을 모두 씁니다.
- 코딩 에이전트가 사용자 이름으로 커밋하는 저장소가 많습니다. `Co-Authored-By` 같은 트레일러, 에이전트 전용 브랜치나 PR 라벨, 커밋 메시지 패턴으로 사람이 쓴 커밋과 에이전트가 만든 커밋을 구분할 수 있는지 봅니다. 구분할 수 없으면 커밋 수, 코드 줄 수를 본인 산출량으로 쓰지 않습니다. 에이전트를 설계하고 운영한 것은 그 자체로 본인 몫입니다.
- 다른 사람이 처음 만든 것과 본인이 넓히거나 고친 것을 구분합니다. "처음 셋업", "최초 연결"을 본인 몫으로 쓰지 않습니다.
- 회사 계정으로 만든 포크나 저장소처럼 작성자를 확인할 수 없는 것은 사용자에게 묻습니다.
- 확인한 크레딧 경계를 `facts`의 해당 프로젝트에 적습니다.

## 3. 숫자 확인

이력서에 쓸 숫자는 계산 방법까지 확인합니다.

- **세는 기준**: 숫자마다 무엇을 셌는지 `facts`에 적습니다. 예를 들어 릴리스 횟수는 버전 번호 변경, 릴리스 커밋, 스토어 출시 중 어느 것인지에 따라 달라집니다. 기준이 없으면 사용자에게 묻습니다.
- **기간과 횟수**: 커밋 날짜, 태그, 릴리스 기록으로 다시 셉니다. "월 3회 이상"처럼 범위를 말하는 표현은 반례가 하나라도 있으면 쓰지 않고 총횟수로 바꿉니다.
- **비율**: 분모와 분자, 측정 조건(도구, 표본 크기, 반복 횟수)을 `facts`에 함께 적습니다. 예비 실험이면 그렇게 적습니다.
- **산출량**: PR 수, 커밋 수, 코드 줄 수는 무엇이 포함됐는지 확인합니다. 문서 PR이 섞여 있으면 문장에 밝힙니다.
- **문제 규모와 결과 구분**: "30일 120건"이 실패 건수인지 개선 후 줄어든 건수인지 구분합니다.

## 4. 원인과 결과 확인

문서에 적힌 원인 분석은 조사 과정의 기록입니다. 그중 무엇이 근본 원인이고 무엇이 악화 요인이었는지는 문서만으로 판단하지 않습니다.

- 초안에 원인 진술을 넣기 전에 "근본 원인은 A, B는 악화 요인"처럼 정리해서 사용자에게 확인합니다.
- 근본 원인이 확정되지 않았으면 "구조 원인 수정", "재발 경로 차단"처럼 확정된 범위만 씁니다.
- 결과("~가 가능해짐", "~를 줄임")는 운영에 반영됐는지 확인합니다. 초안 상태의 설계 문서만 있으면 사용자에게 묻습니다.

## 5. 질문 목록

근거로 확인할 수 없는 사실은 질문 목록으로 모아 한 번에 묻습니다. 질문마다 왜 필요한지 한 줄을 붙입니다.

```text
- 목록 로딩 80% 단축은 캐시 효과인가요? 기준값은 몇 초였나요? (리뷰어가 렌더링 개선과 섞였다고 지적)
- 번들 도구 교체 전후 빌드 시간을 알 수 있나요? (교체 이유를 숫자로 보여 줄 수 있음)
```

답을 받으면 `facts`에 적고, 답하지 않은 질문은 `facts`의 `확인 필요` 절에 남깁니다.

## 6. 공개하지 않을 사실

사용자가 공개하지 않기로 한 값은 `facts`의 `제약` 절에 적습니다. 지표가 작아서 원값을 숨기는 경우가 흔합니다. 이때는 원값 대신 그 데이터로 내린 결정이나 바뀐 행동을 결과로 씁니다.
