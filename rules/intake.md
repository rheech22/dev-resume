# 처음 실행

사용자가 이미 가진 이력서에서 시작합니다. 사용자는 파일을 직접 열어 채우지 않습니다. agent가 대화로 묻고, 답을 `facts`와 workspace에 기록합니다.

`facts` 파일이 없거나 비어 있으면 어떤 모드로 요청을 받았든 이 절차를 먼저 진행합니다. 다만 사용자가 급한 일(예: "이 문장 하나만 고쳐줘")을 요청했으면 그 일을 먼저 하고, 끝난 뒤 처음 실행을 제안합니다.

## 1. 기존 이력서 받기

사용자에게 지금 쓰는 이력서를 달라고 합니다. 형식은 가리지 않습니다.

| 받은 것 | 읽는 방법 |
| --- | --- |
| PDF | `adapters/pdf.md`. 이후 편집 방식(마크다운으로 옮기기, 변경 목록만 주기)을 함께 정합니다 |
| Notion 페이지 | `adapters/notion.md`. 연결된 워크스페이스와 계정이 사용자 본인 것인지 먼저 확인합니다 |
| docx, 한글 문서 | 변환 도구로 텍스트를 뽑거나, 사용자에게 PDF로 달라고 합니다 |
| 마크다운, 텍스트 | 그대로 읽습니다 |
| URL | 웹 페이지를 읽습니다. 로그인이 필요하면 PDF로 달라고 합니다 |
| 이력서 서비스 | `adapters/`에 맞는 문서가 있으면 그 방법으로 읽습니다 |

어디에서 어떤 형식으로 관리하는지 확인해서 workspace의 `source`와 `format`에 적습니다. 사용자에게 파일을 고치라고 하지 않습니다.

## 2. 사실로 쪼개기

이력서를 읽고 경력, 프로젝트, 불릿을 사실 단위로 쪼개 `facts`에 넣습니다. 양식은 `templates/facts.md`입니다.

- 기존 이력서의 문장은 확인된 사실이 아니라 주장입니다. 모든 항목의 상태를 `이력서 기재`로 둡니다.
- 숫자는 숫자만 따로 적고, 무엇을 센 숫자인지 모르면 `확인 필요`에 질문으로 남깁니다.
- 문장을 고치지 않고 원문 그대로 옮깁니다. 다듬는 일은 `write` 모드가 합니다.
- 기존 이력서 안의 모순(섹션마다 다른 날짜, 요약과 본문의 다른 숫자 등)은 `확인 필요`에 질문으로 넣습니다.
- 템플릿에 없는 섹션(수상, 발표, 오픈소스 기여 등)이 있으면 같은 형식으로 절을 추가합니다.

## 턴 나누기

처음 실행은 보통 세 번의 대화로 끝납니다. 한 번에 모든 것을 묻지 않습니다.

1. **첫 턴**: 이력서를 쪼개 기록한 뒤 방향 추정, 편집 방식, 공고, 근거 자료, 공개하지 않을 값을 한 번에 묻고 멈춥니다. 사실 하나하나에 대한 질문은 아직 하지 않습니다.
2. **둘째 턴**: 답을 기록하고 근거 자료로 확인한 뒤, 근거와 다른 사실을 질문 5~7개로 묻고 멈춥니다.
3. **셋째 턴**: 답을 기록하고 정리 결과를 보여 줍니다.

사용자가 중간에 다른 작업(리뷰, 문장 고치기)을 요청하면 그 작업으로 넘어갑니다. 남은 질문은 `확인 필요`에 두고 다음에 이어서 묻습니다.

## 3. 커리어 방향 추정과 확인

이력서를 바탕으로 방향을 추정해서 보여 주고 확인을 받습니다.

```text
이력서로 보면 이런 방향으로 읽힙니다.
- 직무: 프론트엔드 엔지니어
- 강점으로 보이는 것: 웹 성능 개선, 디자인 시스템
- 덜 드러나는 것: 앱 출시, 운영 자동화

이 방향이 맞나요? 지금 이력서와 다른 방향으로 가고 싶으신가요?
(예: 프로덕트 엔지니어, 풀스택, 특정 도메인)
```

- "다른 방향으로 가고 싶은가"는 추정이 맞아 보여도 꼭 묻습니다. 이직을 준비하는 사람은 지금 이력서와 다른 방향을 원하는 경우가 많습니다.
- 답을 `facts`의 `지향` 절에 적습니다. 지향 직무, 원하는 회사 유형, 앞세우고 싶은 경험, 줄이고 싶은 경험입니다.
- 사용자가 답하지 않으면 추정을 `지향`에 적고 "추정"이라고 표시합니다.

## 4. 공고와 근거 자료

두 가지를 함께 묻습니다. 둘 다 없어도 진행합니다.

- **지원할 공고가 있나요?** 있으면 원문을 `<home>/jobs/<회사>.md`에 저장합니다.
- **근거로 볼 수 있는 자료가 있나요?** 저장소, 문서, 메신저, 이메일, 파일, 화면 캡처 무엇이든 됩니다. 받는 절차는 `rules/evidence.md`의 "자료 받기"를 따르고, 읽는 방법을 workspace의 `sources`에 적습니다. 퇴사한 회사처럼 볼 수 없는 경력은 사용자 확인으로 대신합니다.

## 5. 확인

근거 자료가 있으면 `rules/evidence.md`의 절차로 `이력서 기재` 항목을 확인합니다.

- 근거와 맞으면 상태를 `근거 확인`으로 바꾸고 출처를 적습니다.
- 근거와 다르면 차이를 질문 목록에 넣습니다. 이력서 문장을 먼저 고치지 않습니다.
- 이력서에 없지만 근거 자료에서 찾은 큰 작업은 `후보`로 적고 사용자에게 넣을지 묻습니다.

## 6. 질문하고 마무리

질문 목록은 한 번에 5~7개까지만 묻습니다. 이력서에 미치는 영향이 큰 것부터 묻고, 나머지는 `확인 필요`에 남겨 다음에 이어서 묻습니다.

마지막에 정리한 내용을 짧게 보여 줍니다.

- 쪼갠 사실 수와 상태별 개수
- 기록한 커리어 방향
- 남은 질문 수
- 다음에 할 수 있는 일: 문장 다듬기(`write`), 리뷰(`review`), 공고 맞춤본(`tailor`)

이후 사용자가 대화로 무엇을 바꾸든("방향을 풀스택으로 바꿀래", "이 숫자는 틀렸어") agent가 `facts`와 workspace를 고칩니다.

## 형식 옮기기

skill을 업데이트하면 템플릿의 형식이 바뀔 수 있습니다. workspace나 `facts` 맨 위의 형식 표시가 템플릿보다 낮거나 없으면 다음을 따릅니다.

1. 사용자에게 형식이 바뀌었다고 알리고, 옮겨도 되는지 묻습니다.
2. 옮기기 전에 원래 파일을 `<home>/versions/`에 날짜를 붙여 복사합니다.
3. 새 템플릿의 절 구성에 맞춰 기존 내용을 옮깁니다. 내용은 지우지 않습니다. 새 템플릿에 맞는 절이 없는 내용은 `기타` 절에 둡니다.
4. 새로 생긴 칸(예: 상태, 메모, workspace의 `design`)은 기존 내용으로 채울 수 있는 것만 채우고, 나머지는 비워 둡니다.
5. 형식 표시를 새 버전으로 바꿉니다.

바뀐 내용은 저장소의 `CHANGELOG.md`에 있습니다.
