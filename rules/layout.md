# 렌더 점검

이력서는 렌더된 모양으로 읽힙니다. 문장을 바꾼 뒤에는 workspace의 `render` 방법으로 다시 렌더해서 확인합니다.

디자인은 사람마다 원하는 것이 다르고, 도구마다 바꿀 수 있는 범위가 다릅니다. 그래서 이 skill은 정답 디자인을 정하지 않습니다.
점검은 세 가지로 나눕니다.

| 무엇 | 기준 | 어디에 |
| --- | --- | --- |
| 누구에게나 해당하는 점검 | 읽히는가, 잘리지 않는가, 일관된가 | 이 문서의 "공통 점검" |
| 사용자의 취향 | 사용자가 고른 모양 | workspace의 `design` |
| 도구가 허용하는 범위 | 무엇을 바꿀 수 있는가 | `format`에 맞는 adapter의 "디자인" 절 |

## 렌더 결과 얻기

- `format`에 맞는 `adapters/` 문서의 렌더 절을 따릅니다.
- 쓸 수 있는 도구가 없으면 사용자에게 PDF나 페이지 이미지를 받습니다.
- 페이지별 이미지와 텍스트 추출본을 함께 둡니다. 이미지는 모양을, 텍스트는 리뷰어 입력과 텍스트 추출 점검에 씁니다.

## 디자인 기록

workspace의 `design`이 `미정`이면 사용자의 취향을 기록합니다. 사용자가 "일단 뽑아 줘"라고 했으면 먼저 렌더하고 결과와 함께 묻습니다. 마크다운으로 옮긴 직후라면 원본 PDF의 모양과 기본 모양을 함께 보여 주고 고르게 합니다. 커리어 방향을 정할 때처럼 agent가 먼저 읽어 내고 사용자가 확인합니다.

1. 지금 렌더 결과에서 모양을 읽어 냅니다: 컬럼, 페이지 수, 폰트, 글자 크기와 밀도, 색, 장식(사진, 아이콘, 막대 그래프 등). 도구로 읽을 수 없는 항목(예: Notion의 페이지 폰트)은 사용자에게 묻거나 `미확인`으로 둡니다.
2. 읽어 낸 모양을 한두 문장으로 보여 주고 묻습니다. 예: "단일 컬럼, 2페이지, 강조색 하나, 촘촘한 편으로 보입니다. 이대로 유지할까요, 바꾸고 싶은 게 있나요?"
3. 바꾸고 싶다는 답이 adapter의 "디자인" 절에서 바꿀 수 없는 것이면 그렇다고 알리고, 가능한 대안을 제시합니다.
4. 확인한 내용을 `design`에 적습니다. 지금 모양과 다른 것을 원하면 그 항목에 `(적용 전)`을 붙이고 지금 모양도 함께 적습니다. 렌더에서 확인되면 표시를 지웁니다.
5. 새 선택이 다른 기록과 부딪치는지 봅니다. 예를 들어 페이지가 거의 꽉 찬 이력서를 2단으로 바꾸면 본문 칸이 좁아져 페이지 수 기록을 넘길 수 있습니다. 부딪칠 수 있으면 기록할 때 함께 알립니다.

이후 사용자가 "더 여유 있게", "색 빼자"처럼 말하면 그때마다 고칩니다.

사용자가 "알아서 해"라고 하면 지금 모양을 그대로 기록합니다. agent의 취향으로 바꾸지 않습니다.

## 취향의 비용 알리기

취향은 사용자가 정합니다. 다만 고른 모양이 읽히는 데 손해를 볼 수 있으면, 기록할 때 한 번 알립니다. 알린 날짜와 사용자의 답을 `design`의 `알린 비용` 줄에 적고, 사용자가 그대로 가겠다고 했으면 다시 말하지 않습니다.

| 선택 | 알릴 점 |
| --- | --- |
| 2단·사이드바 | 일부 채용 시스템과 텍스트 추출에서 읽는 순서가 섞일 수 있습니다 |
| 이미지 속 글자, 아이콘만 있는 연락처 | 텍스트로 추출되지 않아 검색과 자동 입력에서 빠집니다 |
| 기술 숙련도 막대·점수 | 근거 없는 자기 평가로 읽히고, 기준을 물으면 답하기 어렵습니다 |
| 작은 글자, 좁은 여백 | 인쇄하거나 화면을 줄여 볼 때 읽기 어렵습니다 |
| 색으로만 구분한 정보 | 흑백 인쇄와 색각 차이가 있는 사람에게 구분이 사라집니다 |

## 공통 점검

| 항목 | 확인 |
| --- | --- |
| 렌더 오류 | 선, 글자, 항목이 서로 겹치거나 잘려 그려지지 않는가. 도구의 렌더 버그로 생기는 일이 많고, 가장 먼저 고칩니다 |
| 페이지 경계 | 섹션 제목이나 소제목만 페이지 끝에 남지 않는가 |
| 잘린 항목 | 불릿 하나가 두 페이지에 걸쳐 잘리지 않는가 |
| 빈 공간 | 강제 페이지 넘김 때문에 페이지 하단이 크게 비지 않는가 |
| 한 줄 넘침 | 마지막 페이지에 한두 줄만 넘어가지 않는가 |
| 짧은 꼬리 줄 | 불릿이나 단락의 마지막 줄에 한두 단어만 남지 않는가. 남으면 스타일이 아니라 문장 길이로 고칩니다 |
| 위계 | 섹션 제목, 항목 이름, 소제목, 본문이 서로 구분되는가. 구분되는지는 늘 봅니다. 구분하는 방법(크기, 굵기, 색, 선)은 `design`에 적혀 있으면 그것을 따르고, 없으면 지금 쓰는 방법 안에서 제안합니다 |
| 일관성 | 같은 종류의 정보가 같은 자리에 같은 모양으로 있는가. 기간, 위치, 링크, 불릿 기호 |
| 굵기 | 불릿 안의 굵은 글씨가 결과 리드에만 있는가. 소제목을 굵은 단락으로 쓰는 것은 괜찮습니다. 결과 리드가 굵지 않으면 이 점검이 아니라 `write` 모드에서 고칠 문장으로 따로 알립니다(`rules/writing.md`) |
| 폰트 | 지정한 폰트가 실제로 들어갔는가. 지원하지 않거나 설치되지 않은 폰트는 조용히 다른 폰트로 바뀔 수 있습니다. 바뀐 폰트가 텍스트 추출을 망가뜨리기도 하니 텍스트 추출 점검과 함께 봅니다 |
| 텍스트 추출 | 추출한 텍스트에서 읽는 순서가 맞고, 이름·연락처·링크가 살아 있는가 |

## 웹 제출

workspace의 `submit`이 공개 링크면 공통 점검 중 페이지에 관한 항목(페이지 경계, 잘린 항목, 빈 공간, 한 줄 넘침)과 "강제 페이지 넘김" 절은 하지 않고 다음을 봅니다.

| 항목 | 확인 |
| --- | --- |
| 페이지 제목 | 첫 화면 맨 위에 보이는 제목에 이름이 있는가. 작업용 표시(테스트, 초안, 날짜)가 남아 있지 않은가 |
| 첫 화면 | 스크롤 없이 보이는 범위에 이름, 연락처, 가장 강한 내용이 있는가 |
| 접힌 내용 | 토글처럼 접힌 채 보이는 곳에 꼭 읽혀야 할 내용이 있는가 |
| 모바일 | 좁은 화면에서 컬럼이 쌓이는 순서가 자연스러운가. 표가 잘리지 않는가 |
| 링크 | 링크가 링크로 보이는가. 주소를 그대로 보이는 것과 이름을 붙인 것이 섞여 있지 않은가 |

화면을 볼 수 없으면 원본 구조로 위 항목을 먼저 보고, 화면 점검은 남은 일로 보고합니다.

## 기록과 비교

`design`에 적힌 항목마다 렌더 결과가 맞는지 봅니다. 예를 들어 "2페이지"인데 3페이지로 넘쳤으면, 글을 줄일지 모양을 조일지 사용자에게 묻습니다. 사용자가 이미 "모양으로 맞춰 줘"라고 했으면 조이되, 조이다가 "취향의 비용" 표의 작은 글자·좁은 여백에 닿으면 그 비용을 함께 알립니다.
`(적용 전)` 항목은 어긋나도 결함이 아니라 남은 할 일로 보고합니다. `design`에 적히지 않은 취향은 판단하지 않습니다. 공통 점검은 `design`과 상관없이 늘 합니다.

## 강제 페이지 넘김

페이지 넘김을 강제하는 규칙은 내용이 바뀌면 틀어집니다.

- 강제 넘김 규칙을 쓰면 무엇을 기준으로 넘기는지 주석을 남깁니다.
- 내용을 고친 뒤에는 강제 넘김 규칙이 아직 필요한지 다시 봅니다. 내용이 줄어 빈 공간이 생겼으면 규칙을 지웁니다.
- 가능하면 강제 넘김 대신 "항목 안에서 넘기지 않음" 규칙을 씁니다. 내용이 바뀌어도 덜 틀어집니다.

## 보고

점검 결과는 페이지별로 짧게 보고합니다. 공통 점검과 기록과의 차이를 나눕니다.

- `edit`이 원본을 직접 고치는 방식이면 고친 것과 고치지 않은 것을 나누고, 고치지 않은 이유를 붙입니다.
- `edit`이 `변경 목록만 줍니다`이면 사용자가 반영할 목록을 우선순위대로 줍니다. 반영한 뒤 새 PDF를 받아 다시 점검합니다. 특히 템플릿, 컬럼, 글자 크기를 바꾸면 페이지 넘김이 모두 달라지므로, 꼬리 줄 같은 세부는 새 PDF에서 다시 봅니다.
