# 모드 판정과 범위

## 모드 고르기

요청에서 사용자가 원하는 결과물을 찾습니다.

| 요청 예 | 모드 |
| --- | --- |
| "이력서 봐줄래?"(처음), "이 이력서로 시작하자", "방향을 바꾸고 싶어" | `intake` |
| "이 프로젝트 내용 넣어줘", "문장 다듬어줘", "처음부터 써줘" | `write` |
| "검토해줘", "리뷰해줘", "면접관이라면 어떻게 볼까" | `review` |
| "이 공고에 맞춰줘", "OO사 지원용으로 만들어줘" | `tailor` |
| "페이지가 애매해", "디자인 다시 보자", "렌더 확인해줘" | `layout` |

한 요청에 여러 모드가 섞이면 순서대로 처리합니다. 예를 들어 "검토하고 고쳐줘"는 `review`를 끝내고 결과를 보고한 뒤 `write`로 넘어갑니다.
`review`의 결과를 사용자가 보기 전에 고치지 않습니다. 사용자가 "전부 반영해줘"라고 하면 그때 `write`로 넘어갑니다.

`review` 결과를 반영할 때는 근거가 확인된 지적만 고칩니다. 사용자만 아는 사실이 필요한 지적은 고치지 않고 질문 목록으로 돌려줍니다.

## 기준의 우선순위

문장과 구성을 정할 때 다음 순서로 따릅니다.

1. **채용 공고**: 공고 맞춤본을 만들 때만 적용합니다.
2. **커리어 방향**: `facts`의 `지향` 절. 기본 이력서는 이 방향을 따릅니다.
3. **일반 원칙**: `rules/writing.md`와 `rules/prose.md`.

`facts`의 `제약`은 순서와 상관없이 항상 지킵니다.

이 순서는 문장을 쓸 때의 기준입니다. 리뷰는 기준을 하나로 고르지 않고, 커리어 방향으로 읽히는지와 공고에 맞는지를 각각 판정합니다.

## 범위

이 skill은 소프트웨어 엔지니어의 한국어 이력서와 경력기술서를 다룹니다. 프론트엔드, 백엔드, 풀스택, 프로덕트 엔지니어, FDE, ML·데이터, DevOps처럼 코드와 저장소로 일의 근거를 남기는 직군이 대상입니다.

다음은 범위 밖입니다.

- 개발 직군이 아닌 이력서
- 자기소개서만 따로 쓰는 일. `tailor` 모드의 짧은 지원 동기는 범위 안입니다.
- 면접 코칭만 하는 일. 리뷰 중에 나온 예상 질문을 메모로 남기는 것은 범위 안입니다.
