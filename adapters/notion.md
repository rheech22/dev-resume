# notion

이력서를 Notion 페이지로 관리하는 경우입니다.

> 이 adapter는 Notion 공식 MCP 서버(`notion-fetch`, `notion-update-page`, `notion-duplicate-page`)로 실제 페이지에서 확인했습니다(0.3.0). Notion API를 직접 호출하는 경우는 확인하지 않았습니다. 다른 동작을 발견하면 이 문서를 고쳐 주세요.

## 연결 확인

편집하기 전에 연결된 워크스페이스와 계정을 확인하고 사용자에게 보여 줍니다. Notion MCP에서는 `notion-get-self`가 워크스페이스 이름, 계정 이름, 이메일을 돌려줍니다.

- 회사 워크스페이스이거나 회사 메일 계정이면 이력서 작업을 하지 않습니다. 이직 준비 자료가 회사 워크스페이스에 남고, 관리자가 볼 수 있습니다.
- 연결된 계정이 사용자 본인이 아니면 작업하지 않고 사용자에게 알립니다.
- Notion 연결이 여러 개면 어느 연결로 작업하는지 workspace의 `source`에 함께 적습니다. 예: `https://… (연결: notion-personal)`.
- 개인 계정 연결이 없으면 사용자에게 개인 계정으로 Notion MCP를 따로 연결하라고 안내합니다. 회사 연결을 개인 계정으로 바꾸게 하지 않습니다.

## 읽기

`notion-fetch`는 페이지 전체를 Notion 마크다운으로 돌려줍니다.

- 굵게는 `**`, 링크는 `[글자](주소)`, 인라인 코드는 백틱, 글자색과 배경색은 `<span color="…">`로 나옵니다.
- 콜아웃은 `<callout>`, 컬럼은 `<columns>`와 `<column>`, 토글은 `<details>`나 `{toggle="true"}`가 붙은 제목으로 나오고, 자식 블록은 탭 들여쓰기로 함께 나옵니다. 토글 안도 펼치지 않고 읽힙니다.
- 결과에 `truncated`나 `unknown_block_count`가 있으면 빠진 블록이 있다는 뜻입니다. 그 블록을 따로 읽습니다.
- `<page>`와 `<database>` 태그는 하위 페이지와 데이터베이스입니다. 프로젝트를 데이터베이스로 정리한 이력서는 각 행도 읽습니다.
- 처음 읽은 결과는 `<home>/versions/`에 날짜를 붙여 저장합니다. 이것이 백업입니다.

## 편집

편집은 `notion-update-page`의 `update_content`(찾아 바꾸기)로 합니다. 블록 ID나 서식 조각 배열은 다루지 않습니다.

- 편집 직전에 다시 읽습니다. `page_last_edited_at`이 지난번 읽은 시각과 다르면 사용자가 Notion에서 고친 것입니다. 바뀐 부분을 먼저 확인합니다.
- `old_str`은 페이지에서 한 번만 나오는 가장 짧은 문자열로 고릅니다. 같은 말이 여러 곳에 있으면 앞뒤 글자를 붙여 하나로 좁힙니다. `replace_all_matches`는 사용자가 모두 바꾸라고 할 때만 씁니다.
- 바꿀 범위에 `**`, 링크, `<span>`이 걸리면 `new_str`에도 그대로 다시 씁니다. 굵은 리드를 붙일 때는 `**리드**:`처럼 콜론을 굵게 밖에 둡니다.
- 페이지 전체를 바꾸는 `replace_content`는 쓰지 않습니다. `<page>` 태그가 빠지면 하위 페이지가 지워지거나 옮겨집니다. 삭제 경고가 나오면 사용자 확인 없이 `allow_deleting_content`를 켜지 않습니다.
- 마크다운의 특수 문자(`~`, `[`, `]`, `*` 등)는 역슬래시로 이스케이프되어 있습니다. `old_str`에도 그대로 씁니다.
- 바꾼 뒤 다시 읽어서 바꾼 문장, 같은 블록의 굵게와 링크, 토글 들여쓰기, 컬럼 태그가 그대로인지 봅니다.

## 공개 상태

Notion MCP로는 페이지가 웹에 게시되어 있는지 알 수 없고, 게시 설정도 바꿀 수 없습니다.

- 처음 실행에서 사용자에게 게시 여부와 제출 방식을 묻고 workspace의 `submit`에 적습니다.
- 게시된 페이지를 고칠 때는 고친 내용이 바로 외부에 보인다고 알립니다.

## 맞춤본

공고 맞춤본은 `notion-duplicate-page`로 만듭니다.

- 결과는 바로 돌아오지만 내용은 몇 초 뒤에 채워집니다. 빈 페이지가 아닐 때까지 다시 읽은 뒤 `update_properties`로 제목을 바꿉니다. 제목의 `[ ]`는 `\[ \]`로 씁니다.
- 사본은 원본과 같은 위치에 생기고 위치는 고를 수 없습니다. 사본의 게시 여부는 사용자가 Notion에서 정합니다.
- 사본 주소를 `<home>/jobs/<회사>.md`에 적습니다.
- 백업을 위해 페이지를 복제하지는 않습니다. 사본이 워크스페이스에 쌓입니다. 백업은 읽기 절의 로컬 저장으로 합니다.

## 디자인

Notion은 모양을 바꿀 수 있는 범위가 좁습니다. `design`을 기록할 때 이 범위 안에서만 제안합니다.

| 바꿀 수 있는 것 | 바꿀 수 없는 것 |
| --- | --- |
| 블록 종류(제목 단계, 불릿, 토글, 콜아웃, 구분선), 컬럼과 비율, 글자색과 배경색, 인라인 코드, 아이콘과 커버 | 임의의 폰트, 글자 크기와 줄 간격의 세부 값, 여백, PDF의 페이지 넘김 위치 |

- 페이지 폰트(기본, 세리프, 모노), 작은 글씨, 전체 너비는 Notion 앱에서만 바꿀 수 있고 MCP로는 읽지도 못합니다. 사용자 화면이나 캡처로 확인합니다.
- 기본 폭(본문 약 720px)에서 두 컬럼으로 나누면 본문 칸이 좁아져 불릿이 서너 줄로 늘어납니다. Notion 화면에서 컬럼 묶음의 바깥 가장자리를 끌면 페이지는 가운데 정렬 그대로 두고 컬럼만 본문 폭 밖으로 넓힐 수 있습니다(측정한 예: 본문 720px, 컬럼 866~914px). MCP의 `ratio`는 컬럼 사이 비율만 바꾸고 이 폭은 바꾸지 못합니다. 컬럼 배치를 만든 뒤 사용자에게 이 조작을 안내합니다.
- 전체 너비는 페이지 전체를 넓혀 가운데 정렬이 사라집니다. 사용자가 원할 때만 권합니다.
- 메타 컬럼(회사, 기간, 태그)은 20~25%면 충분합니다. 본문 칸을 넓게 둡니다.
- Notion은 한글을 단어가 아니라 글자 단위로 줄바꿈합니다. 줄 끝에서 단어가 잘리거나 마지막 줄에 한두 글자만 남으면 문장 길이로 고칩니다.
- 토글은 웹에서도 접힌 채 보입니다. 꼭 읽혀야 할 내용은 토글 밖에 둡니다.
- 컬럼은 좁은 화면에서 왼쪽부터 세로로 쌓입니다.

### 레이아웃 참고

Notion 이력서는 종이를 흉내 낸 한 줄짜리 문서보다 Notion의 장점(컬럼, 색, 인라인 태그, 넓은 화면)을 살린 배치가 잘 읽힙니다. 아래는 한국 개발자 Notion 이력서에서 자주 쓰는 배치입니다.

- 새 Notion 이력서를 만들거나, 다른 형식에서 옮기거나, 사용자가 모양을 바꾸고 싶어 할 때 이 배치를 기본 제안으로 씁니다. 사용자가 고르면 `design`에 적습니다.
- 사용자가 이미 쓰는 구조가 있고 바꾸자는 말이 없으면 그 구조를 따릅니다.
- 배치만 바꾸고 문장은 고치지 않습니다. 강조를 새로 넣는 곳은 사용자에게 보여 줍니다.

| 배치 | 모양 | 알릴 점 |
| --- | --- | --- |
| 제목에 소개 | 페이지 제목을 "한 줄 소개, 이름입니다."로 씁니다 | 공개 링크에서 가장 먼저 보이는 줄입니다. 작업용 표시를 남기지 않습니다 |
| 프로필 두 컬럼 | 왼쪽 좁은 컬럼에 연락처, 오른쪽에 소개나 핵심 역량 | 사진을 넣으면 `rules/layout.md`의 "취향의 비용"을 알립니다 |
| 회사별 두 컬럼 | 왼쪽 좁은 컬럼(20~30%)에 회사명, 직함, 위치, 기간. 오른쪽에 프로젝트 | 모바일에서 회사 정보가 프로젝트 위로 쌓이는지 봅니다. 회사마다 비율을 같게 맞춥니다 |
| 컬럼 수 섞기 | 긴 항목(경력, 프로젝트)은 메타·본문 두 컬럼, 짧은 항목(사이드 프로젝트, 학력)은 두세 개를 나란히 | 나란히 둔 항목은 길이가 비슷해야 빈 공간이 덜 생깁니다 |
| 색 | 강조색 하나를 섹션 표시(제목 옆 점)와 소제목에, 회색을 보조 정보에, 강조색 배경을 결과 리드에 | 색은 강조색 하나와 회색만 씁니다. 색으로만 구분하지 않고 굵기도 함께 씁니다 |
| 섹션 구분 | 큰 제목 앞에 구분선 | 구분선과 빈 블록을 겹쳐 쓰면 간격이 들쭉날쭉해집니다 |
| 보조 정보 | 기간과 위치를 회색 기울임으로 | |
| 기술 태그 | 프로젝트 제목 아래 인라인 코드로 `React` `TypeScript` | 주요 기술 규칙(`rules/writing.md`)을 그대로 따릅니다. 깊게 답할 수 없는 기술은 넣지 않습니다 |
| 강조 | 굵게나 배경색 | 불릿 안 강조는 결과 리드 한 곳만 씁니다. 한 불릿에 여러 번 쓰면 무엇이 결과인지 흐려집니다 |
| 키워드별 일하는 방식 | 키워드 제목과 설명 단락 | 태도 주장은 근거 사례가 필요합니다(`rules/writing.md`). 사례 없는 단락만 남지 않게 합니다 |

## 렌더 점검

Notion MCP에는 화면 캡처와 PDF 내보내기가 없습니다. 제출 방식(workspace의 `submit`)에 따라 점검 대상이 다릅니다.

| 제출 방식 | 점검 대상 |
| --- | --- |
| 공개 링크 | 웹 화면. 브라우저 도구가 있으면 공개 링크를 데스크톱과 모바일 너비로 열어 봅니다. 없으면 사용자에게 두 너비의 화면 캡처를 받습니다. `rules/layout.md`의 "웹 제출" 점검을 따릅니다 |
| PDF 내보내기 | 사용자가 Notion에서 내보낸 PDF. Notion 화면과 다르게 나올 수 있으니 PDF 자체를 봅니다. 이후 `adapters/pdf.md`의 렌더 점검을 따릅니다 |

화면을 받기 전에는 마크다운으로 구조만 점검합니다(첫 화면에 보이는 블록, 토글에 접힌 섹션, 컬럼 순서, 링크 표기, 굵게 위치). 화면 점검은 남은 일로 보고합니다.

## 교열 검사

읽은 마크다운에 바로 `scripts/check-copy.mjs`를 돌립니다. 굵게가 `**`로 남아 있어 콜론 위치 검사도 동작합니다. `<callout>`, `<columns>` 같은 태그 줄은 결과에서 무시합니다.
